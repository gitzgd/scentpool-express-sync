# 退货快递公司自动识别

## 目标

门店员工新增退货时只填写快递单号，不再人工选择快递公司。系统先调用快递100智能单号识别，再使用识别结果查询实时物流，减少快递公司与单号不匹配造成的查询失败。

## 数据与状态

- `return_orders.express_company_source` 记录快递公司的来源：历史数据为 `manual`，新建待识别记录为 `auto_pending`，识别成功后为 `kuaidi100`。
- `return_orders.express_company_code` 保存快递100返回的官方公司编码，例如申通为 `shentong`。物流查询直接使用该编码，不再依赖电子面单支持列表。
- 新建退货先持久化业务数据，再执行识别和物流查询。外部接口失败时仍返回已保存的退货单，避免员工因重复提交产生冲突。
- 新建记录、历史来源为 `manual` 的记录、没有快递公司的记录，以及物流状态为“查询失败”的记录会执行识别。这样旧记录即使当前显示“等待揽收”，也会在下次查询时纠正人工误选的快递公司。
- 历史记录重新识别遇到临时故障时，系统会继续用已保存的快递公司查询，避免识别接口波动让原本可用的物流查询中断；识别和旧公司查询都失败时才组合显示两项明确原因。
- 快递100返回的第一候选承运商作为识别结果。只要候选包含有效公司编码，就使用该编码查询快递100支持的承运商；圆通、京东和顺丰的限制仅属于电子面单功能，不限制退货物流查询。

## 页面与接口

- 门店新增退货页移除快递公司选项，只保留单号、联系电话、备注和商品。
- `POST /api/returns` 忽略旧客户端可能提交的 `express_company`，创建后立即识别并查询，返回最新退货状态。
- 退货看板将自动结果标为“快递100识别（仅供参考）”，避免把算法识别展示为人工确认事实。
- 识别或查询失败时，退货单保留“异常/查询失败”状态，并直接显示中文失败原因；总部任务状态同时提供核对单号或联系管理员的处理建议。识别成功后不会再用历史保存的错误快递公司兜底查询。

## 权限和安全

- 退货数据权限不变：门店只能访问本店记录，总部可以访问全部门店。
- 单号和接口密钥不写入日志、测试输出或文档；识别请求使用已有的 `SCENTPOOL_KUAIDI100_KEY`。
- 失败不会删除或改写退货商品、备注和原始单号。

## 迁移与回滚

- 启动时为旧数据库增量添加 `express_company_source` 和 `express_company_code`，不重建退货表；圆通、京东和顺丰历史记录会自动回填现有官方编码。
- 回滚旧代码不会读取新列，已有退货数据仍可使用；但新代码创建的待识别记录可能没有快递公司，回滚后需要总部人工处理。

## 验收

- 新建退货时即使旧客户端提交错误的快递公司，也以快递100识别结果为准。
- 识别为申通等电子面单列表以外的公司时，仍能使用 `shentong` 等官方编码完成物流查询并在看板显示公司名称。
- 历史“人工快递公司 + 查询失败”记录重新查询后可以更新公司和物流状态。
- 历史“人工快递公司 + 等待揽收”记录也会重新识别；识别服务暂时失败时仍可使用旧公司兜底查询。
- 识别失败仍返回已保存记录，并在看板显示明确原因和下一步操作。
- 旧数据库启动后历史退货记录来源为 `manual`。
- 在桌面和手机宽度检查新增退货、退货看板、长单号、多商品和长失败原因。
