# 操作体验与后台稳定性

状态：两阶段本地合成回归与界面验收已通过，等待分阶段发布。此文档不代表生产已具备下述能力。

## 目标与边界

普通保存和页面切换不等待第三方物流接口；耗时工作有明确进度、失败原因和可恢复的持久状态。后台更新不能覆盖员工未保存的输入，也不能重复创建业务单据。

维持 Python 单体、SQLite WAL、门店/团队权限和现有面单规则。不修改 PDF 下载与合并、打印 50 单上限、历史时间字段、不批量确认异常、不升级套餐。

## 两个发布点

1. 操作体验与查询可靠性：请求生命周期隔离、局部进度更新、输入保护、重复提交核对、持久物流查询与旧结果保护；列表、退货、批次预览分页作为完整前后端契约一并验收。
2. 容量与观测：请求头/请求体总时限、快速过载反馈、有界导出和运行指标、日报时间精度兼容、区分网站故障与证据缺失。

每个发布点必须通过本地回归；发布前核实准确生产服务并完成在线备份和完整性检查。阶段间不能部署接口不兼容的半成品。

## 不可破坏的约束

- 面单成功结果不能因为物流查询队列繁忙而回滚或丢失；保存结果和后续查询意图具备事务一致性。
- 查询开始后的单号、电话、取消或重新出单变化，必须使旧查询结果失效，包括单号 A→B→A 的情况。
- 同一任务重试不能重复建单。不能确定提交结果时保留表单，先核对原请求，不自动换新请求标识再次提交。
- 任务状态、详情、分页、汇总、预览和导出均在服务端执行归属校验。
- 页面显示范围与批次处理范围要明确区分；分页不能静默把“全部匹配订单”变成“当前页”。
- 后台轮询不重建整页，不能清空编辑内容、选择或把旧筛选结果覆盖到新页面。
- 异常与无数据保持真实；套餐限制不能解释为网站停机，也不能把缺失指标填成零。

## 上线与回退

上线前后仅核对脱敏聚合、Schema、权限和健康状态，不用生产单据做破坏性测试。上线后需要至少一个完整业务日观察；即时健康检查不能代替全天内存和任务恢复验收。

代码回退必须识别待运行的持久任务并保留业务结果，不能通过删除队列或整库覆盖恢复旧版。数据库恢复需另行授权，不能覆盖上线后新增的真实订单。
