# 售后与合作发货

## 目标与入口

普通销售、售后和合作寄送共用发货、面单队列、打印与物流流程；业务类别与处理状态分别显示。

| 类型 | 编码 | 归属 |
| --- | --- | --- |
| 门店订单 | `standard` | 实体门店 |
| 售后补发 / 换货寄出 | `resend` / `exchange` | 原门店 |
| 博主合作 / 合作样品 | `influencer` / `sample` | 合作团队 |
| 历史未分类 | `legacy` | 原归属不变，仅供迁移前记录 |

- 门店保留普通发货 `/submit`，新增售后发货 `/special/new`；从原发货或退货看板发起可自动关联。
- 合作团队登录直接进入合作寄送，仅能创建和查看本团队记录，不能创建退货或门店销售单。
- 总部“门店与团队”新增单位类型和账号创建；实体门店与团队数量分别展示。迁移不自动创建账号或默认密码。
- 总部统一后台按大类 / 具体类型筛选；列表、汇总、异常提醒、打单预览、导出都有文字分类。手机卡片首先显示类型、归属及状态。

## 数据和权限

`shipment_types.py` 执行幂等增量迁移：`stores.kind`、发货分类/内部说明/合作项目/原单及退货外键、明细的 `item_kind/material_spec`；增加分类及关联索引和 `shipment_submissions` 幂等表。不重建旧表、不猜测历史类别，不改历史商品、备注、状态或业务时间。

创建时读取数据库中的单位类型而非相信前端；门店账号的 `store_id` 强制取自会话。关联记录必须存在且同属所选门店，总部也不能跨门店关联。提交后分类、归属和原始关联不可变；有售后关联的原单不能删除。

新特殊单自动生成 `AS-` / `CO-` 随机编号并复用现有业务 ID 格式。网络超时后同单位、同随机提交标识、同内容返回已有记录；不同内容返回 409。创建与幂等记录在同一 `BEGIN IMMEDIATE` 事务完成；删除后保留空引用，迟到重试不会重建。客户端只在 sessionStorage 保存随机标识，不持久化客户信息；错误保留内存草稿。页面重载后若此前结果未知，需先查列表，再选择“开始另一张新单”。

特殊单允许目录商品与临时物料混合，每单最多 100 项；临时物料名称、规格各最多 100 字，数量必须为 1–999999 正整数。名称与规格作为订单快照进入现有货品摘要，不写入商品目录；普通发货、退货仍使用目录商品。

## 内外信息分离与状态

- `internal_note`、`cooperation_subject` 仅作为内部业务信息展示，不传入面单备注、自定义打印区或分类统计，也不进入普通导出。
- `remark` 保持原有可打印包装要求语义，表单明确标注会给收件人看到。
- 商品、包装备注与内部说明的修改共用“待处理且尚未进入面单流程”的锁定规则。
- 原单发起仅预填可取得的收件信息，寄送明细必须重新选择。退货一般只有电话，不能把退货备注猜测成收件地址。
- 关联退货未签收显示醒目提醒，不改变发货状态，也不阻止总部核对后寄出。退货签收后重新读取会自动去掉提醒。
- 不增加退款、审批、库存扣减；取消面单仍必须获得供应商确认。

## 接口与统计

- `POST /api/shipments` 扩展上述字段；`PATCH /api/shipments/{id}/context` 只修改特殊单内部原因和合作项目。
- 查询、汇总、导出与预览共用 `shipment_group` / `shipment_type` 筛选；非法或互相矛盾的分类返回中文错误。`original_shipment_id` / `related_return_id` 用于关联反查。
- 切换分类清空批量下单、批量打印旧勾选。批次提交时服务端在事务内重新验证每个选中 ID 属于当前筛选范围。确认提示按实际选中记录显示各类数量，单次打印 50 单及内存保护不变。
- CSV/XLSX 在原字段后追加大类、具体类型、归属类型和关联编号，不改变旧列顺序。仅总部可导出。
- 日报旧总量字段不变，新增 `shipment_classification.by_type/by_group`，每类含新建、发货、签收、当前积压数量，时间口径与原总量一致。`by_store` 增加 `store_kind`，团队不伪装成实体店。历史日末事件口径沿用已有 `historical` 字段，不把当前积压称作过去日末。
- 固定采集器白名单保留新增分类聚合；不返回原因、项目、合作对象、客户或订单标识。

## 验收与上线

`special_shipments_test.py` 使用合成数据覆盖：跨单位读取/关联/修改拒绝、团队类别约束、非法数量/归属、并发幂等与删除后重试、已下单锁定、同一分类的分页/汇总/导出/预览、打单范围变化、临时物料摘要、内部信息不进入面单/导出/日报、旧库迁移和完整性。已接入完整 `smoke_test.py`。

本地验收提供三个合成案例：仅补寄包装盒、未签收退货换货、目录商品与临时拍摄物料混寄。演示进程不启动自动任务，并阻断真实面单、物流、打印调用；案例和测试账号只在本地，不提交数据库或部署演示入口。

发布前必须核对正确 Render 服务、完成 SQLite 在线备份并校验完整性、数量及权限；发布后核对健康、历史数量及 `legacy` 分类和权限。无新增环境变量、无真实物流/面单测试。需要由总部创建实际合作团队账号，密码独立安全交付，不在迁移中植入默认密码。

## 回滚

新增列有兼容默认值，但旧版本不理解临时物料、团队权限和内部用途。尚无新特殊单时可回退代码并保留新增 Schema；**产生特殊单后不可简单运行旧版本继续编辑/打单**。优先禁用新入口并发布兼容修复；必须回退时先停止相关写入，在受控副本验证数据与权限兼容。整库恢复另需明确授权及维护窗口，会丢失备份后的业务，不作为自动回滚。
