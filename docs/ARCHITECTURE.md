# 系统架构

## 总览

系统是一个轻量单体应用：Python HTTP 服务提供静态页面和 JSON API，SQLite 保存业务数据，原生 JavaScript 渲染门店端和总部端界面。生产环境运行在 Render 单个 Web Service 上，数据库位于持久磁盘。

```text
浏览器
  ├─ 门店端：发货、发货看板、退货
  └─ 总部端：订单、退货、门店、商品、电子面单设置
        │
        ▼
server.py
  ├─ 登录与权限
  ├─ 页面和 API 路由
  ├─ 导出、备份、恢复、诊断
  ├─ 物流与电子面单后台工作线程
  └─ 批量面单 PDF 编排
        │
        ├─────────────┬─────────────┐
        ▼             ▼             ▼
   database.py    tracking.py    shipping.py
        │             │             │
        ▼             └──────┬──────┘
     SQLite WAL              ▼
                         快递100 API
                              │
                              ▼
                         label_pdf.py
                       短生命周期子进程
```

## 模块职责

### `server.py`

- HTTP 入口、静态文件和 API 路由。
- 登录会话、角色检查和请求响应。
- CSV/XLSX 导出与附件命名。
- 数据库备份、受控恢复和健康检查。
- 独立 Bearer 鉴权的脱敏业务日报路由；该令牌不进入会话或其他管理员权限链。
- 物流同步与电子面单队列工作线程。
- 批量面单下载、子进程合并和流式返回。
- 固定请求线程池和慢请求日志。

### `database.py`

- SQLite 建库、兼容迁移和索引。
- 用户、门店、商品、发货、退货、设置、批次和回调事件的数据访问。
- 门店归属、订单状态、重复单号等业务校验。
- 电子面单任务状态、授权快照和打印状态持久化。
- 在线备份、完整性检查和诊断统计。
- 通过 SQLite URI `mode=ro` 与 `PRAGMA query_only=ON` 提供独立的日报聚合读取。

### `tracking.py`

- 快递100物流查询客户端。
- 签名、响应归一化、状态文本和脱敏配置输出。
- 将供应商响应转换成系统使用的物流状态。

### `shipping.py`

- 快递100电子面单授权、网点、下单、取消和复打客户端。
- 电子面单货品摘要、备注和自定义区生成。
- 回调签名校验与公开配置状态。

### `label_pdf.py`

- 验证可信面单地址。
- 下载并合并面单 PDF。
- 在 Linux 中限制合并子进程内存。
- 通过短生命周期进程确保 PDF 对象和 malloc arena 被操作系统回收。

### `manage.py`

- 本地密码重置、摘要、生产数据库导出、备份和诊断命令。

### `xlsx_importer.py`

- 读取商品 Excel，归一化分类、名称、条码、价格和启用状态。

### `static/`

- `index.html`：单页应用外壳。
- `app.js`：路由、API 调用、状态管理和页面交互。
- `styles.css`：响应式布局和 Apple 风格视觉系统。

### `smoke_test.py`

- 使用合成数据库和模拟快递100响应覆盖主要业务流程。
- 包含旧库迁移、权限、发货、退货、物流、电子面单、取消、复打、打印、导出、备份和生产启动约束。

## 数据模型

主要表：

- `stores`：门店。
- `users`：总部和门店账号。
- `sessions`：登录会话。
- `products`：商品目录。
- `shipments` / `shipment_items`：发货单和商品快照。
- `return_orders` / `return_items`：退货单和商品快照。
- `shipping_settings`：寄件信息、授权和承运商配置。
- `shipping_batches` / `shipping_batch_items`：批量下单队列和结果。
- `shipping_callback_events`：打印等回调事件审计。
- `label_auth_sessions`：电子面单授权会话。

数据库使用 WAL。列表接口避免返回完整物流和下单原始报文；详细物流按需加载。

## 关键数据流

### 门店创建发货单

1. 门店登录并获得绑定的 `store_id`。
2. 前端提交收件信息、门店订单号、备注和商品数量。
3. 服务端重新验证身份、必填字段、商品和重复订单号。
4. 数据库事务写入发货单和商品快照。
5. 门店和总部看板从各自权限范围读取记录。

### 总部批量电子面单

1. 总部按筛选条件生成可下单预览。
2. 服务端创建持久化批次和逐单任务。
3. 后台线程逐单读取寄件设置、承运商授权和订单快照。
4. 快递100成功后保存单号、任务 ID、面单地址、取消授权快照和打印状态。
5. 发货状态更新后触发一次物流查询。

### 取消并重新下单

1. 使用原下单任务保存的授权参数请求取消。
2. 只有供应商明确成功才清空旧单号并恢复待处理。
3. 供应商拒绝时保留旧单号和锁定状态。
4. 确认取消后的新下单使用新的请求 ID。

### 批量打印

1. 总部选择待打印订单。
2. 服务端限制订单数量和下载总量。
3. 独立子进程下载并合并 PDF。
4. 主进程流式发送结果，随后更新打印状态。

### 脱敏业务日报

1. 请求必须精确命中日报路径，并通过独立的 `SCENTPOOL_AUDIT_TOKEN` Bearer 鉴权；普通总部会话不能替代，日报令牌也不参与其他路由鉴权。
2. 服务端按 `Asia/Shanghai` 严格解析单个 `YYYY-MM-DD` 参数，拒绝重复、额外、超长或非法参数。
3. `database.py` 只打开独立 URI `mode=ro` 连接并启用 `query_only`，不调用初始化、迁移或普通写连接。
4. 响应只包含汇总数字、门店名和固定口径元数据。覆盖式状态无法还原历史积压或历史失败事件，因此这些字段明确标为当前快照。

该能力已于 2026-08-05 部署到正确生产服务 `scentpool-express-sync-ec7c`；部署证据与只读生产验收结果记录在 `docs/STATUS.md`。

## 生产拓扑

- GitHub：`gitzgd/scentpool-express-sync`。
- Render：Python Web Service，区域和具体服务状态需由运维任务实时核实。
- 持久磁盘：`/var/data`。
- 生产数据库：`/var/data/scentpool.db`。
- 商品工作簿：`/var/data/products.xlsx`。
- 外部服务：快递100物流查询和电子面单接口。

仓库配置描述了预期拓扑，不代表外部服务当前一定与配置一致。生产状态以带日期的运维验证记录为准。

## 扩展边界

继续使用单体和 SQLite，直到出现经验证的迁移触发条件，例如数据库锁冲突、多实例需求、恢复点要求或数据库容量门槛。任何框架、数据库或部署迁移都应作为独立项目处理，包含数据验证、双写或维护窗口、回滚和生产验收。
