# 系统架构

## 总览

系统是一个轻量单体应用：Python HTTP 服务提供静态页面和 JSON API，SQLite 保存业务数据，原生 JavaScript 渲染门店端和总部端界面。生产环境运行在 Render 单个 Web Service 上，数据库位于持久磁盘。

```text
浏览器
  ├─ 门店端：发货、发货看板、退货
  └─ 总部端：订单、退货、门店、商品、电子面单设置
        │
        ▼
server.py
  ├─ 登录与权限
  ├─ 页面和 API 路由
  ├─ 导出、备份、恢复、诊断
  ├─ 物流与电子面单后台工作线程
  └─ 批量面单 PDF 编排
        │
        ├─────────────┬─────────────┐
        ▼             ▼             ▼
   database.py    tracking.py    shipping.py
        │             │             │
        ▼             └──────┬──────┘
     SQLite WAL              ▼
                         快递100 API
                              │
                              ▼
                         label_pdf.py
                       短生命周期子进程
```

## 模块职责

### `server.py`

- HTTP 入口、静态文件和 API 路由。
- 登录会话、角色检查和请求响应。
- CSV/XLSX 导出与附件命名。
- 数据库备份、受控恢复和健康检查。
- 独立 Bearer 鉴权的脱敏业务日报路由；该令牌不进入会话或其他管理员权限链。
- 物流同步与电子面单队列工作线程。
- 批量面单下载、子进程合并和流式返回。
- 固定请求线程池和慢请求日志。

### `database.py`

- SQLite 建库、兼容迁移和索引。
- 用户、门店、商品、发货、退货、设置、批次和回调事件的数据访问。
- 门店归属、订单状态、重复单号等业务校验。
- 电子面单任务状态、授权快照和打印状态持久化。
- 任务异常分类、版本指纹和人工确认记录；人工确认不修改业务状态。
- 只追加、无个人字段的审计状态事件；为日报提供前向完整的历史日末与失败恢复证据。
- 在线备份、完整性检查和诊断统计。
- 通过 SQLite URI `mode=ro` 与 `PRAGMA query_only=ON` 提供独立的日报聚合读取。

### `tracking.py`

- 快递100物流查询客户端。
- 签名、响应归一化、状态文本和脱敏配置输出。
- 将供应商响应转换成系统使用的物流状态。

### `shipping.py`

- 快递100电子面单授权、网点、下单、取消和复打客户端。
- 电子面单货品摘要、备注和自定义区生成。
- 回调签名校验与公开配置状态。

### `label_pdf.py`

- 验证可信面单地址。
- 下载并合并面单 PDF。
- 在 Linux 中限制合并子进程内存。
- 通过短生命周期进程确保 PDF 对象和 malloc arena 被操作系统回收。

### `manage.py`

- 本地密码重置、摘要、生产数据库导出、备份和诊断命令。

### `xlsx_importer.py`

- 读取商品 Excel，归一化分类、名称、条码、价格和启用状态。

### `static/`

- `index.html`：单页应用外壳。
- `app.js`：路由、API 调用、状态管理和页面交互。
- `styles.css`：响应式布局和 Apple 风格视觉系统。

### `smoke_test.py`

- 使用合成数据库和模拟快递100响应覆盖主要业务流程。
- 包含旧库迁移、权限、发货、退货、物流、电子面单、取消、复打、打印、导出、备份和生产启动约束。

## 数据模型

主要表：

- `stores`：门店。
- `users`：总部和门店账号。
- `sessions`：登录会话。
- `products`：商品目录。
- `shipments` / `shipment_items`：发货单和商品快照。
- `return_orders` / `return_items`：退货单和商品快照。
- `shipping_settings`：寄件信息、授权和承运商配置。
- `shipping_batches` / `shipping_batch_items`：批量下单队列和结果。
- `shipping_callback_events`：打印等回调事件审计。
- `label_auth_sessions`：电子面单授权会话。
- `task_alert_acknowledgements`：异常当前版本的人工确认记录，不保存收件或快递个人数据。
- `audit_event_meta`：审计事件启用时间、首个完整上海自然日和 Schema 版本。
- `audit_state_events`：发货状态、面单、物流和打印的规范化状态事件；只保存内部整数记录号、固定状态/原因分类和时间，不保存业务编号、个人字段、密钥或原始报文，并由数据库触发器禁止更新和删除。
- `shipments` 的发货/签收时间证据列：保存 `exact`、`estimated` 或 `legacy_unclassified` 及固定来源。
- `shipment_time_repair_events`：历史时间修复的只追加审计，只含内部整数记录号、字段、旧值摘要、替换时间、证据等级/来源、批次与指纹，不含业务编号、个人字段或原始报文。

数据库使用 WAL。列表接口避免返回完整物流和下单原始报文；详细物流按需加载。

## 关键数据流

### 门店创建发货单

1. 门店登录并获得绑定的 `store_id`。
2. 前端提交收件信息、门店订单号、备注和商品数量。
3. 服务端重新验证身份、必填字段、商品和重复订单号。
4. 数据库事务写入发货单和商品快照。
5. 门店和总部看板从各自权限范围读取记录。

### 总部批量电子面单

1. 总部按筛选条件生成可下单预览。
2. 服务端创建持久化批次和逐单任务。
3. 后台线程逐单读取寄件设置、承运商授权和订单快照。
4. 快递100成功后保存单号、任务 ID、面单地址、取消授权快照和打印状态。
5. 发货状态更新后触发一次物流查询。

后台面单线程独占一条长期 SQLite 连接，只在本线程内复用；空闲时退避等待，新建或重试批次使用进程内事件即时唤醒。等待期间不保持事务，避免空队列反复创建连接和解析完整 Schema。

### 取消并重新下单

1. 使用原下单任务保存的授权参数请求取消。
2. 只有供应商明确成功才清空旧单号并恢复待处理。
3. 供应商拒绝时保留旧单号和锁定状态。
4. 确认取消后的新下单使用新的请求 ID。

取消成功同时清空发货/签收时间及证据字段；重新出单后按新的面单成功观察建立估算发货时间。所有物流、人工、面单和兼容迁移写入统一校验时间完整性与顺序。

### 批量打印

1. 总部选择待打印订单。
2. 服务端限制订单数量和下载总量。
3. 独立子进程下载并合并 PDF。
4. 全局锁保证同一时刻只有一个合并任务；主进程内存高于安全阈值时在启动子进程前明确拒绝。
5. 主进程流式发送结果，随后更新打印状态。

### 总部异常提醒

1. `GET /api/admin/task-alerts` 从面单、物流、退货物流、打印和长等待的当前字段计算异常，并按电子面单、物流查询、打印分类。
2. 浏览器每 60 秒只刷新提醒数据；当前失败字段恢复后，提醒自然不再返回，不需要额外清理业务记录。
3. `POST /api/admin/task-alerts/resolve` 使用异常标识和版本指纹确认当前这一次异常，写入 `task_alert_acknowledgements`，但不修改订单、快递单号或任务状态。
4. 同一异常的原因或对应更新时间变化后会生成新指纹，旧确认不再匹配，提醒重新出现。两个接口均只允许总部会话访问。

### 脱敏业务日报

1. 请求必须精确命中日报路径，并通过独立的 `SCENTPOOL_AUDIT_TOKEN` Bearer 鉴权；普通总部会话不能替代，日报令牌也不参与其他路由鉴权。
2. 服务端按 `Asia/Shanghai` 严格解析单个 `YYYY-MM-DD` 参数，拒绝重复、额外、超长或非法参数。
3. `database.py` 只打开独立 URI `mode=ro` 连接并启用 `query_only`，不调用初始化、迁移或普通写连接。
4. 数据库触发器从启用时保存一份脱敏旧库快照，随后只追加发货、面单、物流和打印状态变化；只有 `completeness.full_day_coverage_from` 起的完整自然日才按事件精确复原。
5. 响应只包含汇总数字、门店名、固定失败分类与口径元数据。覆盖开始前或迁移当天的历史值仍明确标为部分观察，绝不把当前字段猜成完整历史。

### 本机固定只读采集器

1. 仓库内 `tools/scentpool_daily_audit_probe.py` 固定生产 Service ID、服务名和 URL，并只允许健康检查、日报及 Render 服务详情、部署、事件、日志和指标的 GET 白名单。
2. 可执行文件只从 Mac 登录钥匙串把 Render API Key 与日报令牌读入内存；仓库、命令参数、标准输出和临时结果都不保存凭据值。
3. 日志只在内存中匹配 OOM、5xx、异常栈、数据库锁、超时和慢请求，输出固定聚合计数，不输出日志正文。
4. 每个外部通道都必须返回 `ok`、`no_data`、`http_error`、`permission_denied`、`schema_changed`、`process_error`、`network_restricted` 或目标不匹配状态；失败时仍输出一份有效脱敏 JSON。

独立令牌和当前快照日报基础版已于 2026-08-05 部署到正确生产服务 `scentpool-express-sync-ec7c`，只追加历史扩展已于 2026-08-17 上线；本分支新增的时间证据等级仍未部署。证据与只读生产验收结果记录在 `docs/STATUS.md`。

## 生产拓扑

- GitHub：`gitzgd/scentpool-express-sync`。
- Render：Python Web Service，区域和具体服务状态需由运维任务实时核实。
- 持久磁盘：`/var/data`。
- 生产数据库：`/var/data/scentpool.db`。
- 商品工作簿：`/var/data/products.xlsx`。
- 外部服务：快递100物流查询和电子面单接口。

仓库配置描述了预期拓扑，不代表外部服务当前一定与配置一致。生产状态以带日期的运维验证记录为准。

## 扩展边界

继续使用单体和 SQLite，直到出现经验证的迁移触发条件，例如数据库锁冲突、多实例需求、恢复点要求或数据库容量门槛。任何框架、数据库或部署迁移都应作为独立项目处理，包含数据验证、双写或维护窗口、回滚和生产验收。
