# 项目背景与业务约束

## 项目目标

万物香铺快递同步系统用于多门店与总部发货部门之间的内部协作。门店提交发货或退货信息，总部统一处理订单、电子面单、物流、打印、导出、备份和异常排查。

系统首先解决的是内部数据一致性和操作效率，不是面向消费者的营销网站。

## 使用角色

### 门店员工

- 登录后只操作和查看所属门店的数据。
- 新建发货需求，填写收件人、电话、地址、门店订单号、备注和商品数量。
- 查看本店发货看板和快递单号。
- 在订单尚未进入下单/发货流程时，按规则修改商品、备注或删除整单。
- 新建和查看本店退货信息。

### 总部员工

- 查看和筛选全部门店订单。
- 维护门店与商品。
- 更新订单状态、快递公司、快递单号和总部备注。
- 配置寄件信息、菜鸟授权网点和电子面单产品。
- 批量下单、合并打印、复打以及在支持的通道中取消面单。
- 同步物流和退货物流。
- 导出 CSV/XLSX、下载数据库备份和查看系统诊断。

## 已实现业务域

售后与合作发货复用现有履约流程：门店用原账号提交补发/换货；合作团队账号仅提交博主合作/合作样品并仅看本团队。总部统一按类别处理，门店与团队分开计数。内部原因/合作项目不上面单，临时物料不进商品目录，原发货与退货同归属关联且不覆盖。历史单保留为“历史未分类”。详见 [功能说明](features/special-shipments.md)。

1. 账号、会话、角色与门店归属。
2. 门店、商品和 Excel 商品导入。
3. 发货单、发货商品和业务 ID。
4. 总部发货处理与门店发货看板。
5. 退货单、退货商品和退货物流。
6. 快递100物流查询、签收同步和问题件展示。
7. 快递100电子面单授权、批量下单、取消、复打和打印状态。
8. 批量 PDF 合并与资源保护。
9. CSV/XLSX 导出、SQLite 在线备份、恢复和诊断。
10. Render 单实例部署、持久磁盘和健康检查。

## 核心业务约束

- 门店数据必须按 `store_id` 隔离；不能只依赖前端隐藏按钮。
- 同一门店同一订单日期下的门店订单号不能重复。
- 订单进入电子面单下单流程或已发货后，不能被不安全地修改或删除。
- 电子面单取消必须由供应商确认成功后才能清空单号和解锁订单。
- 取消后重新下单必须使用新的请求标识，失败重试仍需保持幂等。
- 物流问题件不会自动把业务订单改成“异常”，避免物流状态误判业务状态。
- 批量打印成功后可标记打印状态；单张历史面单仍可用于复打。
- 商品导入使用条码作为稳定标识；发货和退货明细保留商品名称、分类等快照。
- 生产数据库和备份含收件人个人信息，不能进入 Git 或非受控存储。

## 当前非目标

- 不把 SQLite 迁移成 PostgreSQL，除非达到 `OPERATIONS.md` 中的触发条件并完成专项评估。
- 不在普通功能任务中更换整个后端框架或前端技术栈。
- 不在代码仓库中保存生产密钥、生产数据库或顾客数据。
- 不把历史任务对话当作当前生产事实来源；外部状态需重新验证。

## 交付标准

一次功能或修复交付至少应说明：

- 用户可见行为和业务边界。
- 修改文件和数据结构影响。
- 权限、状态流转和失败路径。
- 本地验证结果。
- 是否需要部署、迁移、环境变量或生产操作。
- 未解决风险和回滚方式。
